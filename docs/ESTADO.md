- **Pantalla manicurista**: `/cumpleanos` con badge en nav; cards de bonos pendientes con acciones Aprobar / No enviar + link WhatsApp con mensaje de cumpleaños.

- **Banner en cita**: cuando la clienta tiene bono en estado `chosen`, la cita muestra el servicio elegido y recuerda aplicar descuento manual.
- **Push PWA**: SW actualizado con handler `push` + `notificationclick`; endpoint `/api/push/subscribe`; componente `<PushManager>` en layout app.
- **Nav**: `/inventario` movido fuera del nav principal (acceso vía URL directa); `/cumpleanos` ocupa ese slot con badge rosa de bonos pendientes.

### Sync cumpleaños desde Google Contacts — detalle

- **Problema resuelto**: clientas ingresadas manualmente (sin importar desde Contacts) no tenían `birthday_date` → el cron nunca les disparaba el bono.
- **Segundo problema resuelto**: si el sync ocurría después de las 5 AM del día del cumpleaños, el bono no se disparaba hasta el año siguiente.

### Row Level Security (RLS) — nota técnica

El aislamiento multi-tenant actual es correcto y suficiente: todas las queries filtran por `tenant_id` (D-11) y una regla ESLint impide acceso directo a `db` fuera de repositorios. RLS añadiría una segunda barrera a nivel de PostgreSQL, de modo que incluso un acceso directo a la DB no pueda leer datos de otro tenant.

**Implementación sugerida cuando se realice:**

```sql
-- 1. Habilitar RLS en cada tabla de negocio
ALTER TABLE clients ENABLE ROW LEVEL SECURITY;
ALTER TABLE appointments ENABLE ROW LEVEL SECURITY;
ALTER TABLE appointment_services ENABLE ROW LEVEL SECURITY;
ALTER TABLE services ENABLE ROW LEVEL SECURITY;
-- ... resto de tablas con tenant_id

-- 2. Política de lectura/escritura por tenant
CREATE POLICY tenant_isolation ON clients
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid);

-- 3. La app setea la variable de sesión al inicio de cada request
-- en src/lib/db.ts, antes de ejecutar queries del tenant
```

**Requiere:** modificar `src/lib/db.ts` para que cada conexión ejecute `SET LOCAL app.tenant_id = '<tenantId>'` antes de las queries de negocio. Las tablas de auth (users, sessions) y sistema (tenants, memberships) quedan sin RLS.

**Prioridad:** baja — no bloqueante para el lanzamiento. Relevante cuando haya múltiples manicuristas reales usando la app.

## 🔑 Fix OAuth 403 — separar scope `contacts.readonly` (2026-06-18)

`src/modules/calendar/google.ts`: el scope `contacts.readonly` (sensible, requiere verificación Google) estaba en `GOOGLE_SCOPES` junto con `calendar.events`. Al conectar Calendar, Google bloqueaba el flujo completo con 403 access_denied incluso para test users.

Fix: se separaron en dos constantes:

- `GOOGLE_SCOPES` — solo `calendar.events` + openid + email (flujo `/api/google/connect`)

`buildAuthUrl` acepta ahora un tercer parámetro `scopes` (default = `GOOGLE_SCOPES`).  
`/api/google/connect-contacts/route.ts` actualizado para pasar `GOOGLE_CONTACTS_SCOPES`.

Resultado: conectar Google Calendar ya no pide el scope sensible → el 403 desaparece.  
La importación de contactos sigue funcionando vía el flujo separado `/api/google/connect-contacts`.

## 🔒 Fix CSP — `unsafe-eval` en dev (2026-06-18)

`next.config.ts`: la directiva `script-src` de la CSP no incluía `'unsafe-eval'`.  
En dev mode, webpack compila módulos con `eval()` para source maps; la CSP lo bloqueaba con un `EvalError` en `react-refresh-utils`, lo que impedía que React hidratara la app → todos los botones muertos.  
Fix: `'unsafe-eval'` añadido **solo en `NODE_ENV=development`** (`isDev` condicional). Producción mantiene la CSP estricta.
